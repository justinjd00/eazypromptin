Done. A 2D pixel art game can run fine on integrated graphics, but only if a few things are decided at the start. The biggest one is something you set up yourself, before Claude Code ever opens the project:

**When you create the project in Godot, pick the "Compatibility" renderer** (OpenGL 3.3). The default "Forward+" renderer is built for 3D on proper GPUs and is overkill and sometimes flaky on Intel/AMD integrated graphics. Compatibility is meant for this case and has everything a 2D pixel game needs. If you already created the project, change it under Project Settings > Rendering > Renderer.

One more practical point: the host's machine does more work (it runs all the enemies, AI and hit checks), so **whoever has the stronger PC should host.** If the laptop is the weaker machine, it should be the one joining.

```markdown
# Pocket Delve — Project Brief

## What this is
A 2-player online co-op roguelite for PC. Top-down 2D pixel art, real-time twin-stick
combat, ~20 minute runs through 3 floors of randomly arranged rooms. Players get
stronger during a run by picking upgrades; between runs they unlock variety, not power.
Tone: cute, bright, colourful. Never dark or gritty.

v1 is for exactly two friends playing over the internet. A Steam release may come later,
so keep the networking swappable, but do NOT build anything Steam-related now.

The game MUST run smoothly on a laptop with integrated graphics. See "Performance".

## Tech stack (fixed, do not change)
- Godot 4 (.NET build), C# only. Never create GDScript files.
- Renderer: Compatibility (OpenGL 3.3). Do not switch to Forward+ or Mobile.
- .NET 8. Namespace root: `PocketDelve`.
- Networking: Godot high-level multiplayer with ENetMultiplayerPeer.
  Players connect via Tailscale IPs, so v1 needs only "Host" and "Join by IP".
- Art/audio: the Ninja Adventure asset pack (CC0) in `assets/ninja_adventure/`.
  16x16 tiles. Use only this pack so the style stays consistent. Before art is wired
  up, placeholder coloured shapes are fine.
- Pixel-perfect setup: nearest-neighbour texture filtering, integer scaling,
  base resolution 480x270 scaled up to the window (stretch mode "viewport").
  The game renders at 480x270 regardless of screen size, which keeps GPU cost tiny.

## Performance (hard requirement)
Target: stable 60 fps on an integrated GPU (Intel UHD 620 / Iris Xe / AMD Vega class)
on a laptop at 1080p, in the busiest room of floor 3, while hosting.

Rendering:
- Use CPUParticles2D, not GPUParticles2D. Keep particle counts small (hit sparks,
  dust puffs). No full-screen particle effects.
- No real-time 2D lights or shadows (no Light2D / LightOccluder2D). Fake lighting with
  sprites and colour if needed.
- No custom full-screen shaders or post-processing (no bloom, blur, glow,
  screen-space effects). Small per-sprite shaders like a white hit-flash are fine.
- Use TileMapLayer for room geometry, not individual Sprite2D nodes per tile.
- Hide or free everything in rooms the players aren't in.

CPU and physics (the realistic bottleneck on a laptop, especially for the host):
- Cap enemies alive at once (start at 40 per room, tune from there).
- Pool projectiles, damage numbers and effects instead of instancing and freeing
  them every time.
- Use simple collision shapes (circles/rectangles) and collision layers/masks so
  only things that can interact are checked against each other.
- Enemy AI should not do expensive work every frame: pathfinding/target selection
  a few times per second is enough, movement every physics frame.
- C#-specific: avoid allocations in _Process / _PhysicsProcess (no LINQ, no new
  lists, no string building per frame) to keep the garbage collector quiet.
  Cache node references in _Ready instead of calling GetNode every frame.

Network (also costs CPU):
- Sync only what's needed, at a sensible rate (positions ~20-30 times per second
  with interpolation, not every frame). Health and state changes via RPC on change,
  not continuous sync.

Settings and checks:
- VSync on by default, plus a frame rate cap option (30/60/uncapped) in the
  volume/settings screen.
- Include a toggleable FPS and enemy-count overlay (e.g. F3) for testing.
- After every milestone, the game is tested on the integrated-graphics laptop.
  If it drops below 60 fps, fixing that comes before the next milestone.

## Network architecture (most important section)
- Listen server: one player hosts and plays, the other joins. Max 2 players.
  The stronger PC should host; the host does all simulation work.
- Host is authoritative for: enemies and AI, spawning, all damage and health,
  downed/revive state, loot, XP, upgrade rolls, room generation, room clear/door state.
- Each client is authoritative for its OWN player movement and aim only. The local
  player moves instantly; position is synced to the other peer and interpolated there.
  Never wait for the host to confirm movement.
- Attacks: the attacking client plays the animation/effect immediately and sends the
  attack to the host via RPC; the host resolves hits and broadcasts results.
- Each run uses one random seed generated by the host and sent to the client.
  All procedural generation uses that seed so layouts match without syncing tiles.
  Never use unseeded randomness for anything gameplay-relevant.
- Use MultiplayerSpawner, MultiplayerSynchronizer and [Rpc] methods.
- Put connection logic behind one interface (e.g. `INetworkTransport` with Host, Join,
  Disconnect, and connection events) so ENet can later be replaced by Steam networking
  without touching gameplay code.
- Handle disconnects gracefully: if the other player drops, return both to the menu
  with a clear message. No reconnect logic in v1.
- Everything must work with 50-150 ms latency. Test with two local instances
  (Debug > Customize Run Instances) and, on Windows, with a lag simulator like clumsy.

## Gameplay
Controls: WASD move, mouse aim, left click attack, space dodge roll
(short invulnerability). Gamepad supported via the input map
(left stick move, right stick aim). All bindings go through Godot's InputMap.

Co-op rules:
- No friendly fire.
- At 0 HP a player is "downed". The partner revives them by standing next to them
  for ~3 seconds. If both are downed, the run ends.
- No player-count scaling: the game is always 2 players, balance for exactly that.

Run structure:
- 3 floors, each with its own tileset look and enemy set, ending in a boss.
- Each floor has 6-8 rooms built from hand-made room templates (separate scenes),
  shuffled and connected randomly using the run seed.
- Room types: combat, treasure, shop, rest (heal), boss.
- Doors lock when players enter a combat room and unlock when it's cleared.
- Both players must be in the next room before it starts (or get pulled in).

In-run progression:
- Enemies give shared XP. On level-up, EACH player independently picks 1 of 3
  random upgrades (rolled by the host, shown only to that player).
  The game does not pause; picking should be quick.
- Target ~30 upgrades for v1. Prefer mechanics over flat stats: projectiles that
  bounce, hits that burn, dodge leaves a trail, etc. Several should synergise.
  Upgrades that multiply projectiles or effects must respect the performance
  caps above (e.g. a max projectile count per player).
- 3-4 co-op upgrades that only make sense with a partner (e.g. dodging through your
  partner heals them).
- 3 starting weapons that play differently: sword (melee arc), bow (projectile),
  staff (slow area spell).
- Upgrades are data-driven: each upgrade is a Godot Resource (.tres) with id, name,
  description, icon, rarity, and an effect hooked up in code. Adding an upgrade
  should not require editing a giant switch statement.

Between runs (no grinding):
- Unlocks add variety: new upgrades in the pool, new starting weapons.
  At most 1-2 tiny permanent stat perks.
- Unlocks are saved on the host as JSON in user://. Only the host's save matters.

## v1 scope
In: host/join menu, full 3-floor run, 3 bosses, ~8 enemy types, 3 weapons,
~30 upgrades, downed/revive, unlocks, basic HUD (both players' HP, XP bar, level,
gold), music and SFX from the asset pack, a run-end screen (win or lose) with
"play again", a small settings screen (volume, fps cap, fullscreen/windowed),
the F3 debug overlay.

Out (do not build): Steam, lobbies, matchmaking, more than 2 players, singleplayer
mode, reconnecting, graphics quality presets, controller rebinding UI, multiple
save slots, character customisation, localisation, achievements.

## Folder structure
    scenes/       main menu, game, rooms/, players/, enemies/, ui/
    scripts/      mirrors scenes/, plus Networking/, Upgrades/, Generation/, Core/
    resources/    upgrades/, weapons/, enemies/ (.tres data)
    assets/       ninja_adventure/ (untouched pack), plus anything extra

One C# class per file, file name matches class name. Keep scenes small and composed
(e.g. Health, Hurtbox, Hitbox as reusable child nodes) instead of giant scripts.

## Build order (one milestone at a time, each must be playable before moving on)
1. Connection: main menu with Host and Join (IP field). Two players spawn in one
   empty room and see each other move smoothly. Disconnect handling.
   Pixel-perfect 480x270 setup, Compatibility renderer, F3 overlay.
2. Combat: one weapon (sword), dodge roll, one enemy type that chases the nearest
   player, damage, health, downed and revive, run-over state. All networked.
   Object pooling in place. Stress test: spawn 40 enemies, check fps on the laptop.
3. Rooms: room templates, seeded floor generation, doors locking/unlocking,
   moving between rooms together. Inactive rooms hidden/freed.
4. Progression: XP, level-up, independent 1-of-3 upgrade picks, first ~10 upgrades.
5. Content: remaining weapons, enemies, 3 floors with distinct looks, 3 bosses,
   shop/treasure/rest rooms, remaining upgrades including co-op ones.
6. Meta: unlock system and save file, run-end screen, settings screen,
   music and SFX pass, final performance pass on the laptop.

## How to work
- Before each milestone, write a short plan and wait for my OK.
- After each milestone, tell me exactly how to test it (including the
  two-instance setup and what fps to expect) and what to look for.
- Keep it simple. No speculative abstractions beyond the network transport
  interface and the data-driven upgrades described above.
- If something in this brief turns out to be a bad idea in practice, say so
  instead of quietly working around it.
```

One honest note: with this setup, the graphics card is very unlikely to be the problem. If the laptop struggles, it'll be the CPU when it's hosting a room full of enemies. That's why the stress test sits in milestone 2, so you find out early, while the fix is still cheap.
